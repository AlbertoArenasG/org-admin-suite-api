# Diseño técnico

## Contrato HTTP definido

`GET /v1/customer-service-records/timeline?from=2026-10-01&to=2026-10-31&match=periods&page=1&limit=100`.

- `from` y `to`: días civiles inclusivos, obligatorios, ISO `YYYY-MM-DD` y fechas reales. `from <= to`; máximo aprobado de 42 días inclusivos. `page`/`limit`/`items_per_page` siguen `PaginationRequestDto`: máximo global de 100 elementos por página y página 10 000.
- `match`: enum opcional `periods | customer_milestones`, por defecto `periods`; cualquier otro valor produce 400. `periods` selecciona cruces de los tramos de cliente y proveedor para Gantt. `customer_milestones` selecciona únicamente recepción o entrega estimada al cliente dentro del rango para Calendario.
- Auth: `JwtAuthGuard`, `PermissionsGuard`, `@RequirePermission('customer_service_records', 'READ')`.
- Envelope `ApiResponseBuilder` con `data` y `pagination:{page,per_page,total,total_pages}`; `total_pages=0` sin coincidencias. Si supera 10 000, el consumidor debe detectar que no puede recorrer todo el conjunto con el DTO compartido. Orden por `customer_service_record_id` ascendente para páginas estables sobre datos sin mutaciones concurrentes. Si hay escrituras mientras se pagina, no se promete snapshot transaccional; el cliente debe poder recargar el periodo.
- Elemento: `customer_service_record_id`, `service_number` numérico, `service_number_display`, `service_type:{service_type_code,name}`, `requested_at`, `customer:{customer_id,name}`, `assets:[{asset_id,name,identifier}]`, `operational_status:{code,name,name_key}`, `customer_delivery:{received_at,estimated_delivery_at,status_materialization}` y `provider:{provider_id,name,delivered_to_provider_at,estimated_return_at,returned_from_provider_at,status_materialization}` o `null`. `service_number_display` se calcula con el formateador de dominio vigente a partir de `service_number`, sin cargar la entidad completa. Ambas materializaciones conservan la forma presentada actualmente (`code,name,name_key,color_hex,source,effective_start_date`); nulas si no existen. El backend devuelve ambos retornos; el frontend toma el real si existe y, en otro caso, el estimado.
- Errores: 400 por rango/fecha/`match`/paginación inválida, 401 sin sesión, 403 sin READ, 500 según manejo central de error. No hay efectos secundarios.

## Semántica de consulta

Base `status=ACTIVE`. Con `match=periods`, coincidencia por unión lógica de los tramos de cliente y proveedor:

1. **Cliente:** `received_at` entre `from` y `to`, o `estimated_delivery_at` entre ambos, o ambas fechas presentes con `received_at <= to` y `estimated_delivery_at >= from` para un periodo que cruza todo el rango.
2. **Proveedor, con retorno real:** `delivered_to_provider_at` entre `from` y `to`, o `returned_from_provider_at` entre ambos, o ambas fechas presentes con `delivered_to_provider_at <= to` y `returned_from_provider_at >= from`.
3. **Proveedor, sin retorno real:** `delivered_to_provider_at` entre `from` y `to`, o `estimated_return_at` entre ambos, o ambas fechas presentes con `delivered_to_provider_at <= to` y `estimated_return_at >= from`. Esta rama exige `returned_from_provider_at` ausente/nulo; no muestra la estimación como extremo efectivo cuando ya hay retorno real.

Con `match=customer_milestones`, solo aplicar las dos comprobaciones puntuales de la rama de cliente (`received_at` o `estimated_delivery_at` dentro del rango); no incluir cruces sin extremos internos ni las ramas de proveedor. Las ramas de proveedor en `periods` solo aplican cuando existe `provider`. La condición por cruce puede incluir fechas invertidas si un extremo cae en rango; se devuelven fechas persistidas sin inventar valores. Cada registro aparece una sola vez, aunque coincidan varios extremos. Fechas ausentes no hacen match por comparación. No aplicar filtros de fecha del listado existente mediante conjunción. Seleccionar solo campos necesarios con proyección/lectura ligera; no cargar adjuntos, documentos de factura, políticas ni usuarios de cliente. Conservar strings `YYYY-MM-DD` sin UTC.

Índices: el schema ya define `status + customer_delivery.estimated_delivery_at` y `status + provider.estimated_return_at`. Añadir `status + customer_delivery.received_at`, `status + provider.delivered_to_provider_at` y `status + provider.returned_from_provider_at` para las ramas faltantes. No hay migración ni modificación de registros. Declararlos en Mongoose no demuestra que existan en la colección: antes de considerar validado el rendimiento, el usuario comprobará en el entorno autorizado los índices efectivos y el plan de consulta. Si el entorno no los crea automáticamente, el usuario decidirá y ejecutará su creación; el agente no ejecutará comandos de escritura en BD. No se presupone un comando de migración ni un `dry-run` para esta declaración de índices.

## Pipeline

Controller → `GetCustomerServiceRecordTimelineRequestDto` → `GetCustomerServiceRecordTimelineQuery` / handler → `GetCustomerServiceRecordTimelineUseCase` → puerto `ICustomerServiceRecordReadRepository.findTimeline()` → adaptador Mongoose → read model del puerto → `CustomerServiceRecordTimelineMapper` → DTO de aplicación → presenter → `ApiResponseBuilder`. El adaptador mapea documentos proyectados al read model del puerto; el caso de uso invoca el mapper de aplicación para producir el DTO sin depender de Mongoose ni del mapper de la entidad completa. Siguiendo `CustomerServiceRecordMapper`, el nuevo mapper usa métodos estáticos y se importa mediante su barril: no es un provider Nest. El handler solo delega. La consulta y la forma de respuesta pertenecen al módulo administrativo actual, sin permisos nuevos.

## Contrato e Impacto Entre Repositorios

Consumidor: futura spec de frontend para la nueva ruta de cinco vistas. Contrato anterior: solo listado administrativo paginado y filtros de fecha independientes. Nuevo contrato: lectura temporal paginada por rango con proyección reducida de cliente y proveedor; `match=customer_milestones` permite a Calendario recibir solo coincidencias dibujables, mientras `match=periods` entrega ambos tramos a Gantt. No se alteran rutas existentes. El backend entregará el handoff en `docs/frontend/customer-service-record-timeline-handoff.md`, registrará la nueva ruta READ en `docs/authorization/feature-permission-catalog.md` y actualizará la colección Postman antes de cerrar la slice del endpoint; frontend validará la integración en su propia spec. Mes y semana son rangos de consumo, no valores de enum HTTP. Solo los hitos de cliente forman eventos del calendario acordado; el tramo de proveedor se usa en el Gantt.

## Estrategia de validación basada en riesgo

| Riesgo | Escenario | Nivel de validación | Evidencia esperada | Responsable |
| --- | --- | --- | --- | --- |
| Pérdida de registros | Fronteras inclusivas, intervalos que cruzan el rango, una fecha por tramo, solo proveedor visible, sin fechas y varias páginas | HTTP manual y revisión estática del filtro | IDs, orden, `total` y páginas coinciden con los casos preparados | Usuario en validación manual; agente en revisión estática |
| Retorno equivocado | Retorno real y estimado distintos; repetir sin retorno real | HTTP manual | El real determina la visibilidad cuando existe; de otro modo se usa el estimado | Usuario |
| Eventos invisibles en calendario | `customer_milestones` frente a coincidencias solo de proveedor y cruces del cliente sin hitos internos | HTTP manual | No aparecen esos registros; `total` y páginas corresponden a los hitos visibles | Usuario |
| Acceso indebido | Sin token, sin READ y con READ | HTTP manual | 401, 403 y 200 respectivamente | Usuario |
| Error de contrato | Fecha inválida, rango invertido o mayor de 42 días, `match` desconocido, paginación inválida | HTTP manual | 400 con el envelope habitual; rango vacío devuelve `data: []`, `total: 0` y `total_pages: 0` | Usuario |
| Rendimiento y datos excesivos | Proyección, índices y filtro OR con orden estable | Revisión estática y lectura operativa de índices/plan de consulta si existe entorno autorizado | No se cargan adjuntos; índices previstos visibles y plan revisado o limitación registrada | Agente en revisión estática; usuario en entorno de BD |
| Compatibilidad | Listado y detalle previos, handoff y colección Postman | Revisión de diff y HTTP manual | Las rutas existentes conservan contrato; handoff y colección coinciden con la respuesta real | Agente y usuario |
